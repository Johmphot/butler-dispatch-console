Read Me

Butler Dispatch Console compares two ways of grouping split travel-party bookings for SAWASDEE Pass's Personal Butler service. Runs entirely in your browser — parsing, matching, and export all happen client-side; the file is never uploaded anywhere. The page starts with an empty booking list — Load sample export populates demo data on demand.

GG19 skill (original)

Reimplements the tier logic in scripts/process_bookings.py from the shipped butler-booking-grouping skill: split-code detection with a same-flight collision guard, hidden split codes in Special Request, multi-pax rows (Other Passengers), note cross-references, then phone/name matching — unioned into travel parties via union-find. Processes any booking with a Status value (Cancelled, Processing, etc. included), same as the real skill's own script.

APS matching engine (new)

Reimplements the matcher from the group-booking-reference-clean-spec requirement as of its 2026-08-25 update.

Duplicate Detection runs first — a booking matching another on primary signal + exact Pax 1 Name (suffix included) + pax count + Meeting Time + all 5 identity fields (Pax 1 Name, Pax 1 Phone, Contact Name, Contact Phone, Contact Email) gets flagged DUPE and excluded from grouping until staff clear it as Not Duplicated from the Review tab, at which point it flows into ordinary matching on the next Process.

A booking with the IndividualBooking toggle on is pulled out next — set from an "Individual Booking" sample-data column, or live from the Mark/Unmark Individual button in Group Check — and never joins a cluster, no matter how strongly it matches. A toggled booking and one the engine simply found no match for share the same INDIVIDUAL badge ("travels alone" either way — the Evidence column says which).

Everything else clusters on Airport + Flight + Meeting Date + Partner. Airport is read off the Booking Number's own Service letter (P/D/H = BKK/DMK/HKT, per booking-id-reference-scheme — the same letter GroupBookingID generation reuses), so two bookings that otherwise match are kept apart if they're at different airports. Partner is waived entirely for a Klook-OCTO-sourced booking (modeled via a "Booking Source" column) — per klook-octo-integration's actual design, that channel never populates Partner at all.

Corroboration is checked across 5 fields (Pax 1 Name, Pax 1 Phone, Contact Name, Contact Phone, Contact Email), each ONLY against its own same-named counterpart — never cross-field, so a booking's passenger name matching another's contact name does not count. Any one of the 5 is enough for review, but reaching High Confidence / auto-group is a stricter, separate bar: Contact Email match and Pax 1 Phone match are both required — Contact Phone does not substitute for Pax 1 Phone. A cluster that clears the bar with only that pair (no other field) gets a borderline spot-check note, same as an unusually large group (that threshold is a placeholder — the real one is still an open Ops calibration question). The Pax 1 Name n/m suffix pattern has no effect on grouping (only Duplicate Detection reads it, and only as an exact string).

Candidate pool is Status = Confirmed only — a Processing or Cancelled booking is never matched, suggested, or grouped (the original logic is unaffected — it processes any non-blank Status).

GroupBookingID format

G<Service>-<Meeting Date YYMMDD>-<4-digit running>, e.g. GP-260821-0001 — Service letter reused from the party's Booking Number, independent of Booking ID otherwise. Running number resets per Service + Meeting Date, assigned in Meeting-time order. Written for AUTO and CONFIRMED parties — a plain REVIEW cluster is still an unconfirmed suggestion, so it gets none; solo bookings get none either. Under the original logic, GroupBookingID doesn't exist — the Group column is a plain sequential label standing in for today's ad-hoc Excel re-grouping.

Review tab

A cluster that reaches Needs Review lands here, where staff can Confirm it into a real, staff-confirmed group (badged CONFIRMED, gets its own GroupBookingID same as an auto-grouped one), Dismiss it permanently from the queue, or Adjust it — pull one booking out of the cluster (it over-matched) before confirming the rest; the removed booking becomes its own standalone entry (badged ADJUSTED) rather than being re-clustered against the other removed bookings.

Suggested Duplicates share this same tab — a booking that matches another on every field apart from Booking ID. Not Duplicated clears the flag permanently for that exact pair. There's no dedicated cancel/void action here — resolve a real duplicate from Booking Details on whichever booking you cancel.

Merge Groups & Connecting Itinerary

From Group Check, staff can Merge Groups — select 2+ existing groups that turn out to be the same party, and every booking across them ends up sharing one canonical GroupBookingID. Always staff-initiated, never automatic.

Link/Unlink Connecting Itinerary cross-references two rounds that are physically connected but can't share a GroupBookingID (different Meeting Dates) — e.g. an Arrival plus an onward connecting flight — as a "Connects to →" indicator without merging their membership. A round can only have one active link at a time.

Both persist across re-processing until you load new data.

Butler Schedule page

One card per round (same grouping as everywhere else), following the confirmed booking-card mockups: a Group card shows a booking-count badge and an editable GroupName in place of a passenger name; every summed quantity on the card (pax, buggy, suggested butler) is the party-level total, not one member's figures. Two status dots — Assigned and Email Sent — are demo-only manual toggles: this prototype has no real butler-assignment state, and doesn't model whether the Phase 2 contact email fires automatically on assignment or from a separate staff action (still open on the requirement page).

The per-card icon row (confirmed 2026-08-27 against separate Arrival and Departure mockups) shows Arrival Gate/Baggage Belt/Buggy/Flower on Arrival cards and Departure Gate/Check-in Counter/Lounge on Departure cards, with Number of Passengers, Checked Baggage, Oversized Baggage, and Pets on both. Only Number of Passengers and Buggy are real — this prototype's GG19/AOT export schema has no Gate, Baggage Belt, Check-in Counter, Checked/Oversized Baggage, Pets, Flower, or Lounge fields, so those render as a dimmed "—" rather than a fabricated number.

PSI tab

Shows the same field set and row grain as the CSV export (one row per service), headed by the date range spanning every booking in the currently loaded file — independent of the Meeting-Time window. Offers the same Confirm / Dismiss / Not Duplicated / Mark Individual actions inline, so it doubles as another place to review from rather than a separate mechanism. Every row stays a fixed height regardless of how long a task's Details (Special Request) text runs — clipped to a few lines by default, with an Expand/Collapse toggle on that one cell when it overflows.

CSV export & display fields

Export fields, in order: Task No. / GroupBookingID / Group Status / Flight Date / Flight Time / Flight Number / Type / Booking Number / Partner / Contact / Pax Name / Details. Contact and Pax Name each pack a name and phone number into one cell rather than spreading across columns; Details carries Special Request only.

Group Check and Review also show each booking's Channel (Website/Mobile/Backoffice — a display-only field, no role in matching) and Partner.

What's not modeled

  • The Duplicate-&-Group/creation-time override of the Confirmed-only rule.
  • Merge's butler-conflict resolution step — this prototype has no butler-assignment state at all; it only ever suggests a headcount, never assigns a named butler to a booking.
